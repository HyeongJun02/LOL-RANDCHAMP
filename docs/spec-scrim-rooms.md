## 0. 한 줄 요약

지금까지 만든 도구는 **혼자 쓰는 계정 단위**였습니다. 여기서부터는 **여러 명이 같이 보는 방 단위**로 바뀝니다. 이건 단순한 기능 추가가 아니라 데이터 소유권이 `사용자 → 방`으로 옮겨가는 구조 변경이고, 돈(포인트)이 오가므로 **클라이언트를 믿을 수 없는 영역**이 처음 생깁니다.

---

## 1. 범위

### 이번에 만드는 것
- 내전 방 (생성 / 입장 코드 / 멤버 / 권한)
- 방 단위 내전 기록 · 시즌 정산
- 끼꼬 포인트 (지급 / 송금 / 내역)
- 또또 (경기 배팅)
- 방 활동 로그 피드
- 사용자 닉네임

### 이번에 안 만드는 것
- 어드민 페이지 (보류. 다만 `profiles.role` 컬럼은 미리 만들어 둠)
- 조합 배팅 → **[결정 필요 A]** 참고
- 실시간 푸시 (폴링으로 대체. 6장 참고)

### 안 건드리는 것
챔피언 랜덤 / 라인 분배 / 랜덤 뽑기는 지금처럼 **로그인 없이** 동작합니다. 내전 방만 로그인 필수입니다.

## 2. 가장 중요한 전제 — 클라이언트를 믿을 수 없다

지금 구조는 **브라우저가 Neon DB를 직접 찌릅니다** (Data API + RLS). 지금까지는 내 데이터만 다뤄서 문제가 없었지만, 포인트가 생기는 순간 이야기가 달라집니다.

> 개발자 도구 콘솔에서 `neon.from('profiles').update({ points: 999999999 })` 한 줄이면 끝입니다.

그래서 **포인트를 움직이는 모든 동작은 클라이언트가 직접 못 하게** 하고, DB 안의 함수를 호출하는 방식으로만 처리합니다.

| 동작 | 방식 |
|---|---|
| 읽기 (기록, 순위, 배당) | 클라이언트 직접 조회 + RLS |
| 포인트 변동 (배팅/송금/정산/지급) | **DB 함수 호출만 허용** |
| 방 생성 / 입장 / 권한 변경 | **DB 함수 호출만 허용** |

`profiles.points`, `bets`, `point_ledger`에 대한 클라이언트의 INSERT/UPDATE/DELETE 권한은 **전부 회수**합니다. 함수는 `SECURITY DEFINER`로 만들어 함수 안에서만 쓰기가 일어납니다.

이 원칙을 어기면 나머지 설계가 전부 무의미해지므로, 구현 중 예외를 두지 않겠습니다.

## 3. 데이터 모델

### 3.1 표

```
profiles          사용자 1행
  user_id PK, nickname, points, role, agreed_fairplay_at, created_at

rooms             내전 방
  id PK, name, join_code UNIQUE, owner_id, version, created_at

room_members      누가 어느 방에 있나
  room_id, user_id, role(owner|admin|member), joined_at
  PK (room_id, user_id)

room_players      그 방에서 뛰는 사람 명단
  id PK, room_id, name, linked_user_id NULL
  UNIQUE (room_id, name)

scrims            경기
  id PK, room_id, mode(aram|normal), status,
  team_a jsonb, team_b jsonb,          -- room_players.id 배열
  winner NULL, total_kills NULL, first_blood_player_id NULL,
  created_by, created_at, locked_at NULL, settled_at NULL

bet_pools         마켓별 집계 (배당 계산용)
  scrim_id, market, selection, total_amount, bet_count
  PK (scrim_id, market, selection)

bets              개별 배팅
  id PK, scrim_id, user_id, market, selection, amount,
  odds NULL, payout NULL, created_at

point_ledger      포인트 변동 내역 (append-only)
  id PK, user_id, delta, reason, ref_id, counterpart_user_id NULL, created_at

room_logs         방 피드
  id PK, room_id, type, payload jsonb, created_at
```

### 3.2 설계 의도

**`room_players`를 따로 두는 이유.** 지금은 경기에 이름 문자열을 넣습니다. 그래서 이름을 바꾸면 전적이 갈라졌고, 이번에 `renamePlayer`로 메웠습니다. 방 단위에서는 처음부터 **id로 참조**해서 이 문제를 없앱니다. 계정이 없는 손님도 `linked_user_id = NULL`로 참가할 수 있습니다.

**`bet_pools`를 따로 두는 이유.** 배당을 계산하려면 "이 선택지에 총 얼마 걸렸나"가 필요합니다. 매번 `bets`를 `SUM`하면 배팅이 쌓일수록 느려집니다. 배팅할 때 집계 행 하나만 갱신하면 배당 조회는 항상 한 줄 읽기입니다.

**`profiles.points`를 두면서 원장(`point_ledger`)도 두는 이유.** 잔액을 매번 원장 합계로 계산하면 내역이 쌓일수록 느려집니다. 잔액은 컬럼으로 들고, 내역은 따로 쌓되 **같은 함수 안에서 함께 갱신**해 어긋나지 않게 합니다.

**`rooms.version`.** 6장(폴링) 참고.

### 3.3 인덱스

| 표 | 인덱스 | 용도 |
|---|---|---|
| `room_members` | `(user_id)` | 내가 속한 방 목록 |
| `scrims` | `(room_id, created_at DESC)` | 방의 최근 경기 |
| `scrims` | `(room_id, status)` | 배팅 가능한 경기 찾기 |
| `bets` | `(scrim_id)` | 정산 |
| `bets` | `(user_id, created_at DESC)` | 내 배팅 내역 |
| `point_ledger` | `(user_id, created_at DESC)` | 내 포인트 내역 |
| `room_logs` | `(room_id, id DESC)` | 피드 페이지네이션 |

## 4. 권한

### 4.1 역할

| 역할 | 할 수 있는 것 |
|---|---|
| **방장** (owner) | 전부. 부방장 임명/해임, 방 삭제 |
| **부방장** (admin) | 경기 생성·팀 구성·배팅 마감·결과 입력, 멤버 관리 |
| **멤버** (member) | 보기 + 배팅 + 송금 |

방장은 넘길 수 있고, 방에 방장은 항상 1명입니다.

### 4.2 입장

1. 방장이 방을 만들면 **6자리 입장 코드**가 생깁니다 (헷갈리는 글자 `0/O/1/I` 제외).
2. 코드를 입력하면 `join_room(code)` 함수가 멤버로 등록합니다.
3. **한 번 들어오면 코드 없이 다시 들어옵니다.** 멤버 목록에 남기 때문입니다.
4. 방장은 코드를 재발급할 수 있습니다. 재발급해도 **기존 멤버는 그대로**입니다.

### 4.3 RLS 요약

- `rooms` SELECT: 내가 멤버인 방만. **`join_code`는 방장·부방장에게만 보이게 별도 뷰로 분리**합니다. 멤버 전원이 코드를 볼 수 있으면 재발급이 무의미해집니다.
- `scrims`, `bets`, `room_logs`, `room_players` SELECT: 그 방 멤버만.
- `bets` SELECT: **정산 전에는 내 배팅만, 정산 후에는 전원 공개.** (요청하신 "누가 얼마 걸었는지 나중에 공개")
- 모든 쓰기: 함수 경유.

## 5. 화면과 흐름

### 5.1 내전 방 목록 `/rooms`
- 내가 속한 방 카드 (이름, 인원, 최근 경기 시각, 내 역할)
- `방 만들기` / `코드로 입장`

### 5.2 방 안 `/rooms/:id` — 탭 구성

| 탭 | 내용 |
|---|---|
| **기록** | 경기 목록, 팀 구성, 결과 입력 (기존 내전 기록지) |
| **정산** | 월별/전체 순위, 숨은 기록 (기존 시즌 정산) |
| **또또** | 배팅 (5.3) |
| **피드** | 방 활동 로그 |
| **설정** | 방 이름, 참가자 명단, 멤버·권한, 입장 코드 (방장·부방장) |

기존 `내전 기록지`·`시즌 정산` 페이지는 **방 안 탭으로 이동**합니다.
→ **[결정 필요 B]** 기존 개인 기록 처리

### 5.3 또또 흐름

```
[방장] 팀 짜고 '배팅 시작'
   ↓  status = betting
[멤버] 배팅   ← 이때 배당률은 안 보임 (5.4)
   ↓
[방장] '게임 시작'
   ↓  status = locked, 배당률 확정·공개, 더는 못 걺
   ( 실제 게임 진행 )
   ↓
[방장] 결과 입력 (승리팀 / 총 킬 / 퍼블)
   ↓  status = settled
전원에게 결과 공개 — 누가 얼마 걸어 얼마 벌었는지
```

### 5.4 배당률을 언제 보여줄 것인가

말씀하신 대로 **배팅 중에는 안 보여주고, 마감 시점에 확정해 공개**합니다.

이건 단순한 UI 선택이 아니라 시스템을 지탱하는 규칙입니다. 배당이 실시간으로 보이면 마감 직전에 유리한 쪽으로 몰리는 눈치싸움이 되고, 늦게 거는 사람이 항상 유리해집니다. 가려두면 모두가 같은 조건에서 겁니다.

배팅 중에는 **참여 인원과 총 배팅액만** 보여줍니다 (분위기용). 선택지별 분포는 숨깁니다.

## 6. 부하 대책 — 폴링

Neon Data API는 REST라서 **실시간 구독이 없습니다.** 방을 같이 보려면 주기적으로 물어봐야 하는데, 그대로 하면 10명이 5초마다 방 전체를 읽어 하루 종일 DB를 두드립니다.

**변경 감지 방식으로 갑니다.**

1. 방에 무슨 일이 생기면(경기 생성/마감/정산/송금/로그) 트리거가 `rooms.version`을 +1 합니다.
2. 클라이언트는 **`version` 한 컬럼만** 주기적으로 읽습니다. 한 줄, 인덱스 PK 조회입니다.
3. 값이 바뀌었을 때만 상세를 다시 가져옵니다.

여기에 더해:

- **탭이 보이지 않으면 폴링 정지** (`document.visibilitychange`)
- 상태별 간격: 배팅 중 **7초**, 그 외 **30초**, 방 밖 **정지**
- 피드는 **커서 기반 20개씩**. 전체를 다시 받지 않습니다.
- `room_logs`는 방당 **최근 500개만** 유지 (초과분 정리)
- **개별 배팅은 로그로 남기지 않습니다.** 정산 시 요약 한 줄만 남깁니다. 이게 로그 쓰기의 대부분을 없앱니다.

## 7. 끼꼬 포인트

### 7.1 규칙

| 항목 | 값 |
|---|---|
| 가입 지급 | 10,000 끼꼬 |
| 내전 승리 | +1,500 |
| 내전 패배 | +1,000 |
| 송금 | 사용자 간, 전액 이동 (수수료 없음) |

- 순위는 **방 안에서만** 봅니다. 전역 순위는 없습니다.
- 송금은 상대가 **같은 방 멤버일 때만** 가능합니다. 모르는 사람에게 못 보냅니다.
- 모든 변동은 `point_ledger`에 남고, 내 내역 화면에서 "누구에게 / 얼마 / 언제"를 볼 수 있습니다.

### 7.2 인플레이션 — 짚고 갑니다

경기 한 판마다 10명에게 1,000~1,500씩, **판당 약 12,500 끼꼬가 새로 생깁니다.** 100판이면 125만 끼꼬입니다. 배팅은 재분배일 뿐 총량을 줄이지 않으므로, 시간이 갈수록 포인트의 의미가 옅어집니다.

다행히 아래 두 가지가 자연스러운 **소각 장치**로 작동합니다.

- 언더/오버 배당 `1.98` (공정값 2.00) → 약 1% 소각
- 퍼블 배당 `인원 × 0.85` (공정값 인원 × 1.0) → 약 15% 소각

이걸로 부족하면 나중에 조절하면 됩니다. 지금 당장 손댈 필요는 없다고 봅니다.
→ **[결정 필요 C]**

## 8. 또또 — 마켓과 배당

### 8.1 승리팀 — 패리뮤추얼 (건 사람들끼리 나눠 갖기)

```
풀    = 이 마켓에 걸린 총액
승자풀 = 적중한 쪽에 걸린 총액

배당률 = 풀 / 승자풀
지급액 = floor(내 배팅액 × 배당률)
```

**예시** — A팀에 70,000 / B팀에 30,000이 걸렸고 B가 이긴 경우

```
배당률 = 100,000 / 30,000 = 3.33배
B에 10,000을 건 사람 → 33,300 끼꼬
```

말씀하신 "많이 걸린 쪽이 낮은 배당"이 자연히 성립합니다. 그리고 이 마켓은 **나간 만큼만 들어오는 제로섬**이라 포인트가 늘지 않습니다.

**예외 처리**

| 상황 | 처리 |
|---|---|
| 적중한 쪽에 아무도 안 걸었다 | 전원 환불 |
| 한쪽에만 걸렸다 | 배당 1.00 → 사실상 환불 |
| 경기 취소 | 전원 환불 |

### 8.2 퍼스트 블러드 — 고정 배당

```
배당률 = round(참가 인원 × 0.85, 2)
```

10명이면 **8.5배**입니다. 공정값(10배)보다 낮게 잡아 소각이 일어납니다.

고정 배당은 시스템이 지급을 책임지므로, 한 사람이 크게 걸면 손실이 커집니다. **마켓당 1인 배팅 상한 2,000 끼꼬**를 둡니다.

### 8.3 총 킬 언더/오버 — 고정 배당 1.98

기준선 **39.5 / 45.5 / 51.5** 세 개, 각각 독립 마켓입니다.

- 45.5가 중심값이라고 하셨으니 이걸 기본으로 놓고, 위아래를 하나씩 둡니다.
- 정수 기준선은 무승부가 생기므로 전부 `.5`로 둡니다.
- 실제 데이터가 쌓이면 기준선을 조정합니다.
- 1인 배팅 상한 **3,000 끼꼬**.

### 8.4 조작 방지

> "배팅에 신경쓰지 않고 경기를 진행하겠다"는 동의를 받아야 배팅 가능

- 방에 **처음 배팅할 때 한 번** 동의를 받습니다 (`profiles.agreed_fairplay_at`).
- 매번 묻지 않습니다. 한 번 동의했으면 그 뒤로는 안 묻습니다.

여기에 하나 더 제안드립니다.

> **자기가 뛰는 경기에서 '자기 팀 패배'에는 걸 수 없다**

방 사람 전원이 선수라 "선수는 배팅 금지"로는 아무도 못 겁니다. 대신 **일부러 지면 이득인 상황만** 막으면 유인이 사라집니다. 자기 팀 승리에 거는 건 허용합니다 — 그건 조작 유인이 아니라 응원입니다.
→ **[결정 필요 D]**

### 8.5 정산

방장이 결과를 입력하면 **DB 함수 하나가 한 번의 트랜잭션으로** 처리합니다.

1. 경기 상태 검사 (`locked`인지, 이미 정산되지 않았는지)
2. 마켓별 배당률 확정 → `bets.odds`에 기록
3. 적중 배팅에 지급, 미적중은 이미 차감된 상태 유지
4. `profiles.points` 갱신 + `point_ledger` 기록
5. `scrims.status = settled`, 참가자에게 승/패 포인트 지급
6. 피드에 요약 한 줄

**중간에 하나라도 실패하면 전부 되돌립니다.** 절반만 지급되는 상황이 없어야 합니다.

정산은 **한 번만** 됩니다. 이미 정산된 경기에 다시 호출하면 아무 일도 일어나지 않습니다 (네트워크 재시도로 두 번 지급되는 사고 방지).

**결과를 잘못 입력했다면?** 방장이 정산을 되돌릴 수 있게 합니다. 지급을 전부 역분개하고 `betting` 이전으로 돌립니다. 되돌린 사실은 피드에 남깁니다.
→ **[결정 필요 E]**

## 결정이 필요한 것들

### [A] 조합 배팅 — **제 판단: 이번엔 넣지 말자**

말씀하신 걱정이 정확합니다. 넣으려면 이런 게 따라옵니다.

- 같은 마켓 내 두 선택은 동시에 못 걸게 하는 규칙 (승리팀 A + 승리팀 B 불가)
- 배당을 곱해야 하는데, 승리팀은 마감 때까지 배당을 모릅니다. 조합 배당을 언제 확정할지가 애매해집니다
- 일부만 취소될 때(경기 무효 등) 부분 환불 처리

**대신 장바구니 UI는 그대로 하겠습니다.** 여러 마켓을 담아서 `배팅 완료`를 누르면 **독립된 배팅 여러 건**이 한 번에 들어갑니다. 손맛은 같고 계산은 단순합니다. 실제로 써보고 조합이 아쉬우면 그때 얹는 게 낫다고 봅니다.

### [B] 기존 개인 기록을 어떻게 할까

지금 각자 계정에 쌓인 내전 기록이 있습니다. 세 가지 중에 골라주세요.

1. **첫 방을 만들 때 기존 기록을 그 방으로 옮긴다** ← 추천
2. 개인 기록 모드를 그대로 두고 방과 별개로 운영 (화면이 두 벌이 됩니다)
3. 기존 기록은 버린다

### [C] 포인트 소각을 더 넣을까

7.2에서 계산한 대로 판당 12,500씩 늘어납니다. 지금 설계의 소각(언오버 1%, 퍼블 15%)으로 충분한지, 아니면 승리팀 마켓에도 수수료를 넣을지. **제 판단은 "일단 이대로 두고 지켜보자"**입니다.

### [D] "자기 팀 패배에 배팅 금지" 규칙을 넣을까

넣으면 조작 유인이 거의 사라집니다. 안 넣으면 자유도가 높습니다.

### [E] 정산 되돌리기를 방장에게 줄까

결과를 잘못 입력하는 일은 반드시 생깁니다. 다만 되돌리기가 있으면 방장이 결과를 바꿔 배팅 결과를 조작할 수 있습니다. 절충안으로 **되돌린 기록을 피드에 남기고 모두에게 보이게** 하는 걸 제안합니다.

### [F] 방 개수 / 인원 제한

무료 DB를 지키려면 상한이 필요합니다. 초안은 이렇습니다.

- 1인당 만들 수 있는 방: **5개**
- 방당 멤버: **50명**
- 방당 경기: **1,000경기**
- 방당 피드: 최근 **500개**

## 구현 순서 제안

한 번에 다 만들면 어디서 틀어졌는지 알기 어렵습니다. 이 순서를 제안합니다.

| 단계 | 내용 | 왜 이 순서인가 |
|---|---|---|
| 1 | `profiles` + 닉네임 + 포인트 지급 | 포인트가 있어야 나머지가 얹힙니다 |
| 2 | 방 · 멤버 · 권한 · 입장 코드 | 그릇을 먼저 |
| 3 | 기록/정산을 방 안으로 이동 | 지금 있는 기능이라 검증이 쉽습니다 |
| 4 | 송금 + 포인트 내역 + 피드 | 포인트 이동을 먼저 검증 |
| 5 | 또또 (배팅 → 마감 → 정산) | 가장 복잡. 앞이 다 돌아간 뒤에 |
| 6 | 어드민 페이지 | 보류 |

4단계까지 끝나면 **포인트가 함수로만 움직인다**는 게 검증됩니다. 그 위에 5단계를 얹는 게 안전합니다.
