# 내전 방 · 끼꼬 포인트 · 또또 기능 명세서

> **v2 — 결정 반영본.** A~F 확정. 이대로 구현 들어갑니다.
> v1에서 바뀐 것: 조합 배팅 제외 확정 / 기존 기록 폐기 / **월간 시즌 초기화 + 명예의 전당 추가** / 자기 팀 패배 배팅 금지 규칙 제외 / 정산 되돌리기 채택 / 각종 상한 확정

## 0. 한 줄 요약

지금까지 만든 도구는 **혼자 쓰는 계정 단위**였습니다. 여기서부터는 **여러 명이 같이 보는 방 단위**로 바뀝니다. 데이터 소유권이 `사용자 → 방`으로 옮겨가고, 돈(포인트)이 오가므로 **클라이언트를 믿을 수 없는 영역**이 처음 생깁니다.

---

## 1. 범위

### 만드는 것
- 내전 방 (생성 / 입장 코드 / 멤버 / 권한)
- 방 단위 내전 기록 · 정산
- 끼꼬 포인트 (지급 / 송금 / 내역 / **월간 초기화** / **명예의 전당**)
- 또또 (경기 배팅)
- 방 활동 로그 피드
- 사용자 닉네임

### 안 만드는 것
- 어드민 페이지 (보류. `profiles.role` 컬럼만 미리 둠)
- 조합 배팅 **[A 확정: 제외]**
- 실시간 푸시 (폴링으로 대체, 6장)

### 안 건드리는 것
챔피언 랜덤 / 라인 분배 / 랜덤 뽑기는 지금처럼 **로그인 없이** 동작합니다. 내전 방만 로그인 필수입니다.

### 없어지는 것 **[B 확정: 기존 기록 폐기]**
- 개인 계정에 쌓이던 내전 기록(`app_state.matches`)을 **버립니다.** 마이그레이션 없음.
- 내전 기록지 / 시즌 정산은 **방 안 탭으로만** 존재합니다. 개인 모드는 사라집니다.
- **팀원 명단(`app_state.roster`)은 남깁니다.** 라인 분배·랜덤 뽑기 같은 비로그인 도구가 계속 쓰기 때문입니다. 방에는 별도의 참가자 명단(`room_players`)이 있습니다.
- 배포 시 기존 `matches` 데이터는 안내 없이 사라지므로, **배포 전에 공지 한 줄** 필요합니다.

## 2. 가장 중요한 전제 — 클라이언트를 믿을 수 없다

지금 구조는 **브라우저가 Neon DB를 직접 찌릅니다** (Data API + RLS). 지금까지는 내 데이터만 다뤄서 문제가 없었지만, 포인트가 생기는 순간 달라집니다.

> 개발자 도구 콘솔에서 `neon.from('profiles').update({ points: 999999999 })` 한 줄이면 끝입니다.

| 동작 | 방식 |
|---|---|
| 읽기 (기록, 순위, 배당) | 클라이언트 직접 조회 + RLS |
| 포인트 변동 (배팅/송금/정산/지급/초기화) | **DB 함수 호출만 허용** |
| 방 생성 / 입장 / 권한 변경 | **DB 함수 호출만 허용** |

`profiles.points`, `bets`, `point_ledger`, `bet_pools`에 대한 클라이언트 INSERT/UPDATE/DELETE 권한은 **전부 회수**합니다. 함수는 `SECURITY DEFINER`로 만들어 함수 안에서만 쓰기가 일어납니다. 구현 중 예외를 두지 않습니다.

## 3. 데이터 모델

### 3.1 표

```
profiles          사용자 1행
  user_id PK, nickname, points, points_month, role,
  agreed_fairplay_at, created_at

app_season        전역 시즌 1행 (초기화 시점 관리)
  id PK(항상 1), current_month, rolled_at

rooms             내전 방
  id PK, name, join_code UNIQUE, owner_id, version, created_at

room_members
  room_id, user_id, role(owner|admin|member), joined_at
  PK (room_id, user_id)

room_players      그 방에서 뛰는 사람
  id PK, room_id, name, linked_user_id NULL
  UNIQUE (room_id, name)

scrims            경기
  id PK, room_id, mode(aram|normal), status,
  team_a jsonb, team_b jsonb,           -- room_players.id 배열
  winner NULL, total_kills NULL, first_blood_player_id NULL,
  created_by, created_at, locked_at NULL, settled_at NULL

bet_pools         마켓별 집계 (배당 계산용)
  scrim_id, market, selection, total_amount, bet_count
  PK (scrim_id, market, selection)

bets
  id PK, scrim_id, user_id, market, selection, amount,
  odds NULL, payout NULL, created_at

point_ledger      포인트 변동 (append-only)
  id PK, user_id, delta, reason, ref_id,
  counterpart_user_id NULL, created_at

hall_of_fame      지난 달 성적 (명예의 전당)
  id PK, room_id, month, user_id, display_name,
  kkiko_points, kkiko_rank,
  scrim_wins, scrim_losses, scrim_rank
  UNIQUE (room_id, month, user_id)

room_logs         방 피드
  id PK, room_id, type, payload jsonb, created_at
```

### 3.2 설계 의도

**`room_players`를 따로 두는 이유.** 지금은 경기에 이름 문자열을 넣습니다. 그래서 이름을 바꾸면 전적이 갈라졌고, 최근에 `renamePlayer`로 메웠습니다. 방 단위에서는 처음부터 **id로 참조**해 이 문제를 없앱니다. 계정 없는 손님도 `linked_user_id = NULL`로 참가합니다.

**`bet_pools`를 따로 두는 이유.** 배당을 계산하려면 "이 선택지에 총 얼마 걸렸나"가 필요합니다. 매번 `bets`를 `SUM`하면 배팅이 쌓일수록 느려집니다. 배팅할 때 집계 행 하나만 갱신하면 배당 조회는 항상 한 줄 읽기입니다.

**`profiles.points`와 `point_ledger`를 둘 다 두는 이유.** 잔액을 매번 원장 합계로 계산하면 내역이 쌓일수록 느려집니다. 잔액은 컬럼으로 들고, 내역은 따로 쌓되 **같은 함수 안에서 함께 갱신**해 어긋나지 않게 합니다.

**`hall_of_fame`에 `display_name`을 박아두는 이유.** 닉네임은 바뀝니다. 지난 시즌 기록은 그때 이름 그대로 남아야 합니다.

### 3.3 인덱스

| 표 | 인덱스 | 용도 |
|---|---|---|
| `room_members` | `(user_id)` | 내가 속한 방 목록 |
| `scrims` | `(room_id, created_at DESC)` | 방의 최근 경기 |
| `scrims` | `(room_id, status)` | 배팅 가능한 경기 찾기 |
| `bets` | `(scrim_id)` | 정산 |
| `bets` | `(user_id, created_at DESC)` | 내 배팅 내역 |
| `point_ledger` | `(user_id, created_at DESC)` | 내 포인트 내역 |
| `room_logs` | `(room_id, id DESC)` | 피드 페이지네이션 |
| `hall_of_fame` | `(room_id, month DESC)` | 명예의 전당 |

## 4. 권한

### 4.1 역할

| 역할 | 할 수 있는 것 |
|---|---|
| **방장** | 전부. 부방장 임명/해임, 코드 재발급, **정산 되돌리기**, 방 삭제 |
| **부방장** | 경기 생성·팀 구성·배팅 마감·결과 입력, 멤버 관리 |
| **멤버** | 보기 + 배팅 + 송금 |

방장은 넘길 수 있고, 방에 방장은 항상 1명입니다.

### 4.2 입장

1. 방을 만들면 **6자리 입장 코드**가 생깁니다 (헷갈리는 `0/O/1/I` 제외).
2. 코드를 입력하면 `join_room(code)` 함수가 멤버로 등록합니다.
3. **한 번 들어오면 코드 없이 다시 들어옵니다.** 멤버 목록에 남기 때문입니다.
4. 방장은 코드를 재발급할 수 있고, **기존 멤버는 그대로**입니다.

### 4.3 RLS 요약

- `rooms` SELECT: 내가 멤버인 방만. **`join_code`는 방장·부방장에게만** 보이도록 분리합니다. 멤버 전원이 코드를 보면 재발급이 무의미합니다.
- `scrims`, `bets`, `room_logs`, `room_players`, `hall_of_fame` SELECT: 그 방 멤버만.
- `bets` SELECT: **정산 전에는 내 배팅만, 정산 후에는 전원 공개.**
- 모든 쓰기: 함수 경유.

## 5. 화면과 흐름

### 5.1 내전 방 목록 `/rooms`
내가 속한 방 카드 (이름, 인원, 최근 경기, 내 역할, 내 끼꼬) + `방 만들기` / `코드로 입장`

### 5.2 방 안 `/rooms/:id`

| 탭 | 내용 |
|---|---|
| **기록** | 경기 목록, 팀 구성, 결과 입력 |
| **정산** | 이번 달 내전 순위 + 끼꼬 순위, 숨은 기록 |
| **또또** | 배팅 |
| **전당** | 지난 시즌 명예의 전당 |
| **피드** | 방 활동 로그 |
| **설정** | 방 이름, 참가자 명단, 멤버·권한, 입장 코드 |

**팀 짜기**는 일반 도구로 남기되(비로그인 사용 가능), 방 안 `기록` 탭에서 경기를 만들 때 **같은 밸런스 로직을 재사용**합니다. `balance.js`가 이미 순수 함수라 그대로 씁니다.

### 5.3 또또 흐름

```
[방장] 팀 짜고 '배팅 시작'
   ↓  status = betting
[멤버] 배팅   ← 배당률 비공개 (5.4)
   ↓
[방장] '게임 시작'
   ↓  status = locked, 배당률 확정·공개, 더는 못 걺
   ( 실제 게임 )
   ↓
[방장] 결과 입력 (승리팀 / 총 킬 / 퍼블)
   ↓  status = settled
전원 공개 — 누가 얼마 걸어 얼마 벌었는지
```

### 5.4 배당률은 마감 때 공개

배팅 중에는 **참여 인원과 총 배팅액만** 보여주고, 선택지별 분포와 배당률은 숨깁니다.

UI 취향이 아니라 시스템을 지탱하는 규칙입니다. 배당이 실시간으로 보이면 마감 직전에 유리한 쪽으로 몰리는 눈치싸움이 되고, **늦게 거는 사람이 항상 유리해집니다.** 가려두면 모두가 같은 조건에서 겁니다.

## 6. 부하 대책 — 폴링

Neon Data API는 REST라서 **실시간 구독이 없습니다.** 방을 같이 보려면 주기적으로 물어봐야 하는데, 그대로 하면 10명이 5초마다 방 전체를 읽습니다.

**변경 감지 방식으로 갑니다.**

1. 방에 무슨 일이 생기면 트리거가 `rooms.version`을 +1 합니다.
2. 클라이언트는 **`version` 한 컬럼만** 폴링합니다. 한 줄, PK 조회입니다.
3. 값이 바뀌었을 때만 상세를 받습니다.

추가로:

- **탭이 안 보이면 폴링 정지** (`visibilitychange`)
- 간격: 배팅 중 **7초**, 그 외 **30초**, 방 밖 **정지**
- 피드는 **커서 기반 20개씩**
- `room_logs`는 방당 최근 **500개**만 유지
- **개별 배팅은 로그로 안 남깁니다.** 정산 시 요약 한 줄. 이게 로그 쓰기의 대부분을 없앱니다.

## 7. 끼꼬 포인트

### 7.1 규칙

| 항목 | 값 |
|---|---|
| 시즌 시작 지급 | **10,000 끼꼬** |
| 내전 승리 | +1,500 |
| 내전 패배 | +1,000 |
| 송금 | 같은 방 멤버끼리, 수수료 없음 |

- 순위는 **방 안에서만** 봅니다. 전역 순위 없음.
- 송금은 **같은 방 멤버에게만**. 모르는 사람에게 못 보냅니다.
- 모든 변동은 `point_ledger`에 남고, "누구에게 / 얼마 / 언제"를 볼 수 있습니다.

### 7.2 월간 시즌 초기화 **[C 확정]**

**매월 1일(KST) 모두의 끼꼬가 10,000으로 돌아갑니다.** 지난 달 성적은 명예의 전당에 박제됩니다.

이걸로 인플레이션 문제가 통째로 사라집니다. 판당 12,500씩 찍혀도 한 달마다 리셋되므로 누적되지 않습니다. 매달 같은 출발선이라 늦게 합류한 사람도 불리하지 않습니다.

**어떻게 돌리나 — 지연 실행**

Neon 무료에는 스케줄러가 없습니다. 크론 대신 **누가 포인트를 건드릴 때 확인**합니다.

```
포인트를 움직이는 모든 함수의 첫 줄:
  ensure_season()

ensure_season():
  app_season.current_month 가 이번 달보다 과거인가?
    아니오 → 그냥 반환 (대부분의 경우, 비용 거의 0)
    예    → roll_season() 실행
```

`roll_season()` 이 하는 일 — **한 트랜잭션 안에서**:
1. 모든 방에 대해, 멤버들의 현재 끼꼬와 지난 달 내전 전적을 `hall_of_fame`에 기록
2. 모든 `profiles.points`를 10,000으로, `points_month`를 이번 달로
3. `app_season.current_month` 갱신
4. 각 방 피드에 "N월 시즌이 끝났습니다" 한 줄

**동시 실행 방지.** 두 명이 동시에 첫 요청을 보내면 두 번 돌 수 있습니다. `app_season` 행에 `FOR UPDATE` 잠금을 걸고, 잠금을 얻은 뒤 달을 다시 확인합니다. 두 번째 요청은 이미 갱신된 값을 보고 그냥 지나갑니다.

**비용.** 한 달에 한 번, 전체 사용자 수만큼의 UPDATE입니다. 9장의 상한 안에서는 무시할 수준입니다.

### 7.3 명예의 전당

방 안 `전당` 탭에 지난 시즌들이 쌓입니다.

```
2026년 9월  🥇 철수  42,300 끼꼬      🥇 영희  12승 3패
2026년 8월  🥇 영희  38,100 끼꼬      🥇 철수  15승 6패
```

끼꼬 1등과 내전 성적 1등을 따로 보여줍니다. 도박을 잘한 사람과 게임을 잘한 사람이 다르기 때문입니다.

## 8. 또또 — 마켓과 배당

### 8.1 승리팀 — 패리뮤추얼

```
풀     = 이 마켓에 걸린 총액
승자풀 = 적중한 쪽에 걸린 총액

배당률 = 풀 / 승자풀
지급액 = floor(내 배팅액 × 배당률)
```

**예시** — A팀 70,000 / B팀 30,000, B 승리

```
배당률 = 100,000 / 30,000 = 3.33배
B에 10,000 건 사람 → 33,300 끼꼬
```

많이 걸린 쪽이 자동으로 낮은 배당을 받습니다. **나간 만큼만 들어오는 제로섬**이라 포인트가 늘지 않습니다.

| 상황 | 처리 |
|---|---|
| 적중한 쪽에 아무도 안 걸었다 | 전원 환불 |
| 한쪽에만 걸렸다 | 배당 1.00 → 사실상 환불 |
| 경기 취소 | 전원 환불 |

### 8.2 퍼스트 블러드 — 고정 배당

```
배당률 = round(참가 인원 × 0.85, 2)
```

10명이면 **8.5배**. 공정값(10배)보다 낮아 소각이 일어납니다.
고정 배당은 시스템이 지급을 책임지므로 **1인 배팅 상한 2,000 끼꼬**를 둡니다.

### 8.3 총 킬 언더/오버 — 고정 1.98

기준선 **39.5 / 45.5 / 51.5**, 각각 독립 마켓입니다.

- 45.5를 중심으로 위아래 하나씩.
- 무승부가 없도록 전부 `.5`.
- 데이터가 쌓이면 기준선 조정.
- 1인 배팅 상한 **3,000 끼꼬**.

### 8.4 조작 방지 **[D 확정: 자기 팀 패배 배팅 금지 규칙은 넣지 않음]**

동의 절차만 둡니다.

- 방에서 **처음 배팅할 때 한 번** 동의를 받습니다 (`profiles.agreed_fairplay_at`).
- 이후로는 묻지 않습니다.
- 정산 후 **누가 뭘 얼마나 걸었는지 전원에게 공개**되는 것 자체가 억제 장치입니다.

### 8.5 장바구니

여러 마켓을 담아 `배팅 완료`를 누르면 **독립된 배팅 여러 건**이 한 번에 들어갑니다. 배당을 곱하지 않습니다.

- 같은 마켓에 두 선택지는 담을 수 없습니다 (승리팀 A와 B 동시 불가).
- 담은 총액이 잔액을 넘으면 결제되지 않습니다.
- 함수 하나가 전부를 한 트랜잭션으로 처리합니다. **일부만 들어가는 일이 없습니다.**

### 8.6 정산

방장이 결과를 입력하면 **DB 함수 하나가 한 트랜잭션으로** 처리합니다.

1. 상태 검사 (`locked`인지, 이미 정산되지 않았는지)
2. 마켓별 배당률 확정 → `bets.odds`에 기록
3. 적중 지급, 미적중은 이미 차감된 상태 유지
4. `profiles.points` 갱신 + `point_ledger` 기록
5. `scrims.status = settled`, 참가자에게 승/패 포인트 지급
6. 피드에 요약 한 줄

중간에 하나라도 실패하면 전부 되돌립니다. **절반만 지급되는 상황이 없어야 합니다.**

정산은 **한 번만** 됩니다. 이미 정산된 경기에 다시 호출하면 아무 일도 없습니다 (네트워크 재시도로 두 번 지급되는 사고 방지).

### 8.7 정산 되돌리기 **[E 확정: 방장에게 부여]**

결과를 잘못 입력하는 일은 반드시 생깁니다.

- **방장만** 되돌릴 수 있습니다 (부방장 불가).
- 지급을 전부 역분개하고 `locked` 상태로 되돌립니다. 배팅은 그대로 남아 있어 다시 결과만 입력하면 됩니다.
- **되돌린 사실이 피드에 남고 모두에게 보입니다.** `21:58 방장이 정산을 되돌렸습니다 (2번째)`
- 되돌린 횟수를 경기에 기록해 표시합니다. 반복되면 눈에 띕니다.

되돌리기가 있으면 방장이 결과를 바꿔 배팅을 조작할 수 있지만, **드러나게 만드는 것**으로 갈음합니다. 친구끼리 쓰는 도구에 이보다 무거운 장치는 과합니다.

## 9. 상한 **[F 확정]**

| 항목 | 상한 |
|---|---|
| 1인당 만들 수 있는 방 | **5개** |
| 방당 멤버 | **50명** |
| 방당 경기 | **1,000경기** |
| 방당 피드 | 최근 **500개** |
| 퍼블 1인 배팅 | 2,000 끼꼬 |
| 언더/오버 1인 배팅 | 3,000 끼꼬 |

**클라이언트가 아니라 DB 함수·트리거에서 막습니다.** 지금 `app_state`에 걸어둔 방식과 같습니다. 앱 쪽 숫자와 DB 쪽 숫자가 어긋나면 화면에서는 되는데 저장이 거절당하므로, 지금처럼 **두 값을 대조하는 테스트**를 둡니다.

## 구현 순서

한 번에 다 만들면 어디서 틀어졌는지 알기 어렵습니다.

| 단계 | 내용 | 왜 이 순서인가 |
|---|---|---|
| 1 | `profiles` · 닉네임 · 포인트 지급 · 시즌 초기화 | 포인트가 있어야 나머지가 얹힙니다 |
| 2 | 방 · 멤버 · 권한 · 입장 코드 | 그릇을 먼저 |
| 3 | 기록/정산을 방 안으로 (기존 개인 기록 제거) | 있는 기능이라 검증이 쉽습니다 |
| 4 | 송금 · 포인트 내역 · 피드 | 포인트 이동을 먼저 검증 |
| 5 | 또또 (배팅 → 마감 → 정산 → 되돌리기) | 가장 복잡. 앞이 다 돌아간 뒤에 |
| 6 | 명예의 전당 | 시즌이 한 번 넘어가야 볼 수 있습니다 |
| 7 | 어드민 페이지 | 보류 |

4단계까지 끝나면 **포인트가 함수로만 움직인다**는 게 검증됩니다. 그 위에 5단계를 얹는 게 안전합니다.

## 남은 위험

구현 전에 알고 있어야 할 것들입니다.

1. **시즌 초기화가 지연 실행이라, 한 달 내내 아무도 안 들어오면 안 돌아갑니다.** 다음 사람이 들어올 때 밀린 달을 한 번에 처리해야 합니다. 여러 달이 밀린 경우도 `roll_season()`이 감당하도록 만듭니다.
2. **정산 함수가 이 시스템에서 가장 복잡합니다.** 여기서 트랜잭션이 깨지면 포인트가 사라지거나 두 배로 생깁니다. 테스트를 가장 두껍게 깝니다.
3. **`app_state`에서 `matches`를 떼면 기존 사용자 데이터가 사라집니다.** 배포 시점에 공지가 필요합니다.
4. 방 하나에 사람이 몰리면 폴링이 곱해집니다. 50명이 7초 간격이면 초당 7회입니다. 상한(50명)을 지키고, 배팅 중이 아닐 때는 30초를 유지합니다.
